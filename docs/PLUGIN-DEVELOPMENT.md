# AI Command Engine 插件开发方案

> 自有项目开发要求 · 2026-10-07
> 适用对象：AI Command Engine 指令、插件内部执行逻辑、本地代理及配套使用文档。
> 本文独立维护，不属于嘉立创官方技能，也不代表官方 SDK 的行为承诺。

## 1. 需求与边界

| 编号 | 要求 | 验收标准 |
| --- | --- | --- |
| R1 | 官方技能保持独立，自有要求写在本方案 | 不通过修改官方技能表达项目要求；资料来源与本地约束有明确区分 |
| R2 | AI 使用简单、稳定的结构化指令，底层操作封装在插件中 | 常规操作只需命令名和业务参数，不要求 AI 临时编写 SDK 执行脚本 |
| R3 | 指令内部正确处理顺序、失败、未知结果和恢复 | 异常路径不假成功，不重复未知写入，不继续依赖后续写入 |
| R4 | 按证据验证 SDK 行为与修复效果 | 文档、类型、模拟、宿主和保存重开证据分别记录 |
| R5 | 功能、使用说明与交付物一致 | 命令说明与实际参数、默认值、结果和错误行为一致；安装包可追溯到验证源码 |

本次仅形成方案，不据此新增代码、限制、重试、心跳、监控、日志或其他机制，不安装或发布插件，不修改现场工程。后续实现仍按具体任务授权执行。

### 官方资料与自有规范

- 官方技能、SDK 声明及原厂资料用来查询 API、参数、枚举、版本和平台限制；不在其中追加本项目开发规则。
- 本方案承载自有的指令设计、执行、恢复、验收和交付要求。发生分歧时记录具体接口和证据，不擅自改写官方说明。
- 官方文档没有说明的行为标为未知，不默认具有取消、原子性、幂等性、同步生效或持久化保证。按本次功能需要做针对性测试。
- 当前本机技能曾经过本地整合，不能称为纯官方原版。本次不做还原或覆盖；如需恢复原版，另行核对来源与差异，保留自有材料。

## 2. 简单指令与内部封装

执行关系：**AI → 本地代理 → 插件指令处理器 → 官方 SDK → EDA 宿主**，结果按原路径返回。

| 部分 | 负责内容 |
| --- | --- |
| AI | 理解目标、选用指令、提供业务参数、编排任务、根据结果决定下一步及验收 |
| 自有使用文档 | 告诉 AI 指令的用途、参数、前置条件、结果含义和异常后的处理方法 |
| 本地代理 | 连接、目标窗口路由、请求转发、回包和已有通信保护 |
| 插件 | 参数核对、调用顺序、SDK 操作、必要读回、结果分类及已有异常停止逻辑 |
| 官方 SDK 与宿主 | 实际操作工程数据、渲染与保存；其行为必须按版本和证据确认 |

### 指令设计要求

1. 面向 AI 暴露明确的业务动作，例如删除图元、移动器件、重建覆铜。参数表达目标与期望，不要求调用者提供底层执行代码。
2. SDK 调用细节、对象类型识别、异步依赖、必要读回和错误处理封装在插件内部。已支持的常规操作，不把底层兼容或时序处理推给 AI 每次重写。
3. 简单指令不等于“一条指令包办整个工程”。AI 仍可按任务组合命令或使用已有宏；设计决策、授权与最终验收仍由调用方负责。
4. 新增或修改指令须明确：名称、用途、目标身份、必填/可选参数、单位、默认值、返回结构、失败含义、是否有副作用以及验证边界。
5. 参数错误明确拒绝；默认值有文档依据。不得静默更改用户输入、降级为另一种操作，或用空值吞掉失败。
6. 优先复用现有指令及执行通道。改变旧命令含义或结果结构时，说明兼容影响，同步调用方文档；不为同一动作另开绕过检查的写入口。

请求示例（占位 ID 需替换成当前核实的值）：

```json
{
  "instanceId": "当前目标窗口ID",
  "cmd": "schematic.delete",
  "params": { "primitiveIds": ["目标图元ID"] }
}
```

删除类型识别、SDK 调用、读回和超时后的停止处理由插件执行。调用方按实际返回判断成功、部分完成或未知，不把收到回包等同于操作成功。

## 3. 执行与恢复要求

### 3.1 目标与顺序

- 沿用现有窗口、工程、文档和页类型检查，执行前核对真实目标。当前 HTTP 指令显式携带 `instanceId`；重连后重新确认，不能照搬旧实例 ID。
- 同一实时文档保持一个写入者，按依赖顺序执行。AI 请求与插件 UI 写请求复用已有执行和状态检查通道。
- 用户切页、目标变化或基线失效后，停止依赖步骤并重新读取，不抢回焦点后盲写。
- 测试实例与正式实例不得争用同一窗口；是否采用独立工程、目录或扩展身份按实际测试方案确定，不随意改变现有安装身份。

### 3.2 结果必须有证据

- 区分未发送、前置拒绝、执行中、结果未知、已应用、已保存、已验证、部分完成和恢复失败。这是结果语义要求，不要求无条件新增状态系统。
- SDK 返回成功、请求已提交、对象可读取、图元已保存是不同证据。不得用任意一项替代其余各项。
- 查询抛错、返回结构非法或缺少必要字段时保留未知；不能当作对象不存在、空网络、空填充或页签已关闭。
- 根据接口语义选择证据：新建对象可按返回 ID 核对；删除不能仅凭可能缓存的单对象查询判断；旧填充不能掩盖本次重建错误。
- 部分完成或未知结果保留已完成项、未处理项、相关 ID、错误及现有任务查询入口，不能只返回模糊的成功提示。

### 3.3 超时和迟到返回

- **超时不等于取消，也不等于没有执行。** 等待结束后，原 SDK 操作仍可能完成。
- 未确认写入期间停止后续依赖写入，包含内部循环、备用通道、健康探针、补偿和宏步骤；不能只停最外层循环。
- 沿用已批准的时间预算。涉及多项操作时核对总耗时和外层等待边界，不在每个子项重新给满预算导致累计越界。
- 在必要的异步等待之后、下一次写入之前及最终成功返回之前检查停止条件；迟到返回不能解除已触发的停止状态。
- 超时参数须符合现有计时机制的有效范围；每项完成后清理本项计时器，避免成功项的旧计时器误停后续项。
- 按现有协议传播部分完成或未知状态。例如当前 `error.cause.partial=true` 应阻止依赖宏继续，即使 `stopOnError:false`；普通前置错误不应无依据标为已经部分写入。

### 3.4 重试与恢复

- 先查询任务状态、只读核对实际内容。对效果未知的写入不直接重发，不通过释放队列或清除标记宣称恢复。
- 需要重试时先确认原调用已结束或可安全隔离，并证明目标效果尚未发生；复用已有操作身份、返回 ID 和结果记录。
- 补偿仅针对确认由本次创建且可独立定位的对象。存在自动合并导线、级联删除或共享对象时，不凭新句柄推断可安全撤销。
- 未证明平台原子性时，不承诺自动回滚必定成功；原调用仍可能运行时，不并发发起恢复写入。
- 不假设存在通用 undo，也不把“不保存关闭”当作可靠回滚。恢复后核对内容，恢复未确认时如实报告。
- 备份、保存、关闭与重开按任务需要和授权执行；只读查询或导出不混入保存、重载。

## 4. 开发步骤与验收

1. **固化需求**：编号列出本次目标、修改范围、不允许修改的部分及可检查的验收结果。已明确授权的工作直接推进，关键需求变化再确认。
2. **取得基线**：记录当前源码、SDK/类型包、宿主及代理版本，保留相关现状和必要备份。先读已有实现，避免重复开发已修复内容。
3. **核实接口**：查目标项目实际安装的声明和对应官方资料，只查本次需要的成员。文档与运行表现不一致时做最小区分测试，保留未知项。
4. **实现封装**：在既有指令内部完成本次逻辑，保持参数及结果一致性。一个文件或实时工程一个写入者；不顺手重构其他模块。
5. **验证并复审**：按受影响路径做正常与异常回归。一次修复仍失败，交同一 expert 做最小区分验证，再修改；不反复猜改。
6. **构建与交付**：检查实际安装包和对应源码；同步自有使用文档，列出完成、待实现、待验证内容。

### 验证层次

| 层次 | 能证明什么 | 不能替代什么 |
| --- | --- | --- |
| 声明与静态检查 | 方法签名、类型及本次代码路径 | 当前宿主一定支持或行为正确 |
| 模拟与故障注入 | 永挂、拒绝、迟到、非法读回、部分完成时的分类与停止逻辑 | 真实 SDK 缓存、后台调度、持久化行为 |
| 构建与包内校验 | 可构建、入口和资源正确、版本及包内程序对应验证源码 | 已安装运行成功 |
| 真实宿主验证 | 指定宿主和测试工程中的实际效果 | 所有版本、对象和工程均适用 |
| 保存关闭重开读回 | 本次对象与属性的持久性 | 板级电气、制造或实物可靠性 |

按本次改动选择必要场景：正常成功、SDK 拒绝、永不返回、迟到返回、读回失败/结构非法、操作发生但报错、目标变化、内部后续写及宏停止。涉及计时器时，验证超时停止和正常多项不被误停。断言实际写调用次数及结果，不只检查错误文本。

检查已通过且源码、依赖和验收对象未变时不重复扩大测试；新改动、失败或具体疑点才触发相应重测。没有做的验证明确标记，不将模拟结果写成实机通过。

## 5. 文档与交付

- **每次更新插件，都必须在同一任务中检查并同步更新该插件对应的自有技能文件**，包括新增功能、缺陷修复和行为调整。AI Command Engine 对应 `ai-command-engine` 技能；按改动更新其 `SKILL.md`、命令参考、使用示例及其他受影响文件，核对命令、参数、默认值、返回值、错误处理和已知限制。不得为同步项目要求修改官方技能。
- 交付前核对插件代码与技能说明一致，列出已更新的技能文件及对应变化。确实不影响技能内容的内部修改，应明确记录“已核对，无需改文档”及原因；不得直接跳过检查，也不为凑记录改无关文字。需要同步而未完成时，不得将插件更新报为全部完成。
- 本方案是开发规范，不复制维护整套指令表；具体命令以对应自有使用文档和已实现代码为准。
- 交付包含：改动文件清单、适用的差异统计、需求编号到实现位置的对应、逐项验证结果、范围外发现及未验证项。
- 检查 `.eext` 的版本、入口、菜单导出和必要资源，排除密钥、工程资料及无关开发文件；需要时记录包及构建输出哈希。
- 安装、真实工程写入、对外发布依据当前任务授权分别执行，构建成功不自动授权发布。
- 结论先说已确认的结果，再说剩余事项，最终由用户确认是否闭环。
